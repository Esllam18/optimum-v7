# Optimum 5.7.0 — Adaptive Workspace / Policy‑Driven UI

## الهدف

هذه المرحلة تحول ميزات الشركة والصلاحيات وحدود الباقة من عناصر واجهة شكلية إلى **سياسة تشغيل فعلية** تشكل تجربة كل شركة وكل عضو.

المعادلة المستخدمة في الواجهة والخادم هي:

`الوصول الفعلي = الشركة فعالة + الميزة مفعلة + الصلاحية الفعلية + نطاق الوصول/RLS + حد الباقة عند العمليات المقيدة`

## المشكلة الجذرية التي تم إصلاحها

الواجهة القديمة كانت تحاول ربط الصلاحية بالميزة من خلال حقل `entitlements.permission_key`، بينما هذا الحقل غير موجود في قاعدة البيانات. الربط الصحيح في النظام هو:

`permissions.entitlement_key -> entitlements.key`

لذلك كان من الممكن أن يتم حفظ تعطيل ميزة الشركة بنجاح في Supabase، بينما تستمر بعض أجزاء الواجهة في الظهور أو العمل.

## مصدر الحقيقة الجديد

تمت إضافة RPC باسم `workspace_runtime_policy(company_id)` يعيد للحساب الحالي:

- حالة تشغيل الشركة.
- الباقة الفعلية.
- الصلاحيات الفعلية بعد احتساب الدور والاستثناءات والميزات.
- كل Entitlement وحالته الفعلية ومصدرها: الباقة أو تخصيص الشركة.
- حدود الأعضاء والمشاريع والتخزين.
- الاستخدام الحالي للأعضاء والمشاريع والتخزين.

الواجهة تعتمد على هذه السياسة في تشكيل نفسها بدل إعادة اختراع منطق الوصول محليًا.

## ماذا يحدث عند إيقاف Module للشركة؟

مثال `module.members`:

- يختفي Team من القائمة.
- لا تظهر إجراءات دعوة/إدارة الأعضاء.
- لا يمكن منح صلاحيات Members جديدة من مصمم الأدوار.
- إذا كانت الصفحة مفتوحة وقت إيقاف الميزة، يتم تحديث السياسة عند رجوع التركيز للنافذة وتحويل المستخدم إلى Dashboard.
- الصلاحيات المرتبطة بالميزة تصبح غير فعالة في الخادم.
- أي زر قديم بقي في DOM بسبب حالة متأخرة يخضع لـ Action Guard قبل التنفيذ.

وينطبق المبدأ نفسه على Files / Projects / Tasks / Engineering / Search وغيرها حسب الـEntitlement والصلاحية المرتبطة.

## Feature‑only entitlements

بعض الميزات لا تمثل Module كاملًا، لذلك تحتاج Gate مباشرًا على العملية نفسها.

تم في هذه المرحلة إغلاق `feature.file_versioning` في جهتين:

- الواجهة: لا يظهر مسار إنشاء إصدار جديد ولا اقتراح استخدام الملف كإصدار جديد عندما تكون الميزة متوقفة.
- الخادم: `begin_new_version_upload` يرفض العملية إذا كانت الميزة متوقفة.

## البحث

- Global Search يظهر فقط عند وجود `search.use` فعليًا.
- النتائج لا تعرض وجهات لا يستطيع المستخدم فتحها.
- RPC `global_search` أصبح يتحقق من `search.use` على الخادم قبل تنفيذ البحث.

## الفلاتر

تم إصلاح Team / Roles / Projects filters لتعمل على DOM الفعلي، مع إصلاح مشكلة CSS كانت تسمح لقواعد `display` الخاصة بالكروت بتجاوز سلوك `hidden`.

الآن:

- Team search + role/status filters تعمل فعليًا.
- Role search/module filters تعمل فعليًا.
- Project search/status filters تعمل فعليًا.
- حالة البحث تحفظ داخل State أثناء إعادة الرسم ذات الصلة.
- الـempty state يظهر عندما لا توجد نتائج.

## حدود الباقة

الخادم كان يملك أصلًا حواجز حقيقية لـ:

- عدد الأعضاء.
- عدد المشاريع.
- التخزين عند رفع الملفات.

5.7.0 أضاف انعكاس هذه الحدود في الواجهة عبر Runtime Policy:

- إظهار الاستخدام الحالي مقابل الحد.
- إخفاء/منع إجراءات الإنشاء عندما يصل الحد.
- Action Guard يمنع تنفيذ زر قديم عند بلوغ الحد.
- الخادم يظل السلطة النهائية ولا يعتمد على الواجهة وحدها.

## Platform Console

واجهة ميزات الشركة أصبحت تشرح الأثر الفعلي لكل Entitlement:

- مصدر الحالة: الباقة / تخصيص الشركة / غير مهيأ.
- عدد الصلاحيات المرتبطة بالميزة.
- هل العنصر Module أم Feature مستقلة.
- Confirmation واضح قبل تعطيل Module يشرح أن التنقل والبحث والإجراءات والصلاحيات المرتبطة ستتأثر.

## Live policy refresh

عند العودة لنافذة Client بعد تعديل المزايا من Platform Console:

- يتم إعادة طلب Runtime Policy عند `focus` أو عودة الصفحة إلى حالة visible.
- إذا تغيرت السياسة يتم تحميل البيانات المسموح بها فقط وإعادة تشكيل الواجهة.
- إذا أصبحت الصفحة الحالية غير متاحة يتم الرجوع إلى Dashboard.

## مبدأ الأمان

إخفاء UI ليس أمانًا. لذلك 5.7.0 يجمع بين:

1. Navigation/UI gate.
2. Action gate.
3. Permission/entitlement gate في قاعدة البيانات.
4. RLS / scope rules للبيانات.
5. Plan-limit enforcement على الخادم.
